# Asterix prompt 迭代结果

本轮完成 6 个候选版本、10 组动作比较：672 次真实订阅模型动作回答，另有 4 次视觉诊断。没有新增付费 API 调用。模型固定指定为 gpt-6.1-sol，沿用订阅 runner 配置。全部模型输入图片哈希与原始因果三帧一致，原始用户标注未修改。

**暂定候选：priority_escape_v6。实时 policy 尚未替换。** 全部 18 个已标核心案例各重复 3 次，v6 标注一致率为 30/54（55.6%），同轮基线 19/54（35.2%）。另外 6 个重点案例各重新回答 5 次，v6 为 16/30，第四版 14/30，基线 5/30。

这些数字衡量原始候选动作集合的一致率。动作不在该集合里，不能自动判定它必然碰撞；动作命中集合，也不能证明整局存活。所有案例都来自先前已看过的 seed 2/5 轨迹，重复调用使用新线程、新响应，图片相同。没有未见轨迹测试、动作替换后的 ALE 分支验证或新的实时游戏。

**仍需解决的问题**

C06a 最终仍有 1/5 输出 RIGHT，C01b 仍有 2/5 输出 RIGHT；迎面方向错误没有清零。C06b 最终没有选择用户标的 RIGHT，而多次选择 UP/UPRIGHT，需要用明确的延迟及后续控制条件复核可接受动作集合。原控制器的换行中断问题未修改，故本轮模型动作改善还不能等同于执行改善。

**独立性和复现方式**

每个调用使用新原生线程，只提供该例原始三帧、原 prompt 的时间条件与已执行动作历史，再替换策略段。没有提供用户答案、场景坐标标签、未来图片、别的案例回答或视觉诊断结果。每版每案例 prompt 哈希在各轮重复间保持不变。

这些是固定截图上的新响应重复，不是新随机种子或独立整局轨迹。订阅响应耗时没有驱动游戏前进；本轮没有复测 ultrafast API 延迟。所有批次都在请求前检查订阅用量，达到 50% 就停止发出新请求。开始观测周用量 24%，结束读数 29%。

评分逻辑的 4 个测试已通过，覆盖多答案集合、无效输出计为失败、重复结果拒绝、未标注及执行诊断案例排除。672 个动作回答均为有效 0–8；4 个视觉诊断单独记录，没有混入动作分母。

复现入口是上层的 `evaluate_case_prompts.py`（需要实验服务器已有 subscription runner 与 suite），汇总入口为 `summarize_case_prompts.py`。详见同目录 `protocol.json`、`remote_run_metadata.json`、`audit.json`、`stageN_results.jsonl` 和 `stageN_summary.json`。策略原文见 [priority_escape_v6.txt](/home/zihan/papers/latency/.codex-worktrees/asterix-policy-state/experiments/sol_ultrafast/policy_cases/prompt_search/priority_escape_v6.txt)。

后续优先项：复核 C06b 等多解案例；针对 C01b/C06a 继续测迎面方向禁选规则；独立修复和验证控制器换行中断；通过整局轨迹后再考虑实时替换。

评测形式参考 [OpenAI 官方评测文档](https://developers.openai.com/api/docs/guides/evals)，本报告中的数据均来自本次项目实测。
